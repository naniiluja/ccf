# Tooling

## Plugin-bundled MCP servers (`plugins/ccf/.mcp.json`)
Two remote HTTP servers, auto started/stopped by Claude Code at plugin scope:
- **context7** (`https://mcp.context7.com/mcp`) — **use when**: you need to look up the schema/contract/syntax of Claude Code, a library, framework, or CLI. Flow: `resolve-library-id` → `query-docs`. Runs without an API key (free rate limit); if rate-limited, set env `CONTEXT7_API_KEY` (free at context7.com/dashboard) and restart Claude Code.
- **microsoft-learn** (`https://learn.microsoft.com/api/mcp`) — **use when**: you need Microsoft/Azure/.NET platform guidance. No auth. Tools: `microsoft_docs_search` (breadth) → `microsoft_code_sample_search` (examples) → `microsoft_docs_fetch` (depth).

> Grounding is a CCF law: before writing a spec/decision about Claude Code's schema or a library, consult the official docs and CITE them, don't rely on memory.

> **shadcn MCP is intentionally NOT bundled here.** The official shadcn server (`npx shadcn@latest mcp`) is **stdio + project-scoped** (it reads the target project's `components.json`), so bundling it at CCF's plugin scope would make it run — and error — in every non-React project. Instead `/ccf:init` writes it into the **target React project's own `.mcp.json`** when the user picks shadcn (same pattern as the Supabase/Railway hosting MCP). Keep this file's count at **2 bundled servers**.

## Grounding subagent
- `ccf-best-practice-researcher` — **use when**: you want to fan out best-practice lookups into a separate context so they don't flood the main conversation. It calls Context7/MS Learn and returns a cited recommendation.

## Internal skill
- `grill-me` (`plugins/ccf/skills/grill-me/SKILL.md`) — **use when**: a command (`/ccf:plan`/`/ccf:init`) needs to interview the user before acting. **How to call**: invoke via the Skill tool, passing the mode (`plan`/`init`) as the argument; it runs the one-question-at-a-time interview and returns a summary. Internal (`user-invocable: false`) — not for direct user invocation; model-invocation stays enabled so commands can call it.

## CCF scripts (human-run CLI, shipped with the plugin)
- **`scripts/archive-plan.mjs`** — **use when**: `PLAN.md` holds an iteration whose every task row is closed and it needs retiring into `ARCHIVE.md`. The Stop hook's clause (D) detects this and prints the exact command; `/ccf:updatespec` step 6 also calls for it. **How to call**: `node "<plugin-root>/scripts/archive-plan.mjs"` to PREVIEW (default, writes nothing — it also names which rows still hold each iteration open), then add `--apply` to perform it. Options: `--dir <path>` (project root; defaults to `$CLAUDE_PROJECT_DIR` or cwd) and `--no-git` (plain `fs.rename` instead of `git mv`). It writes ARCHIVE.md BEFORE trimming PLAN.md, so an interrupted run duplicates history rather than losing it; it stages the moved task files and **never commits**. It does NOT trim `CLAUDE.md`'s `## Current plan` — it prints that as the remaining manual step, because deciding what the new lead iteration is takes judgment.

## CCF scripts, continued
- **`scripts/jev-slice-check.mjs`** — **use when**: the `plan` skill's task files exist and you want an advisory read on hidden dependencies between OPEN tasks, tasks that share a contract, and tasks too small to stand alone. **How to call**: `node "<plugin-root>/scripts/jev-slice-check.mjs" [--dir <path>]` with `TYPESAFE_API_KEY` set; it prints JSON (`edges`, `fragments`, `skipped`, `unanswered`, `waves`, `parallel_candidates`, `note`) and always exits 0 (`no-key`, `no-plan`, `not-enough-tasks`, `too-large`, `error` are reasons in the JSON, never failures). Read-only: it edits no file. Code decides `file-overlap` (after `{a,b}`/glob expansion; an unparseable path clashes with everything), `unknown-files` (a task with no `Files to touch`) and `hotspot` (both tasks touch one class: lockfile, migration, generated file, barrel export, shared config, shared spec), and those pairs are never asked. `dependency`, `contract` and `shared-state` are Jev's judgment at 0.3, and a pair missing any answer is `unanswered`, i.e. a dependency (fail-closed, task 065). A `parallel_candidates` wave has no edge at all, yet Jev's recall is unmeasured, so it is a candidate only. Sends task ids, titles, files and criteria (no source code) to `api.typesafe.ai`.
- **`scripts/jev-verify-findings.mjs`** — **use when**: a `/ccf:check` report carries `FAIL:` findings and you want Jev's advisory read on whether the diff really contains each one. **How to call**: `node "<plugin-root>/scripts/jev-verify-findings.mjs" [--dir <path>] [--base <ref>] < report.md` with `TYPESAFE_API_KEY` set (`/ccf:check` step 6b does this for you). It prints JSON with every finding, its Jev score and a `verdict` (`confirmed`, `not-confirmed`, `unjudged`), and always exits 0. It only annotates: a finding Jev does not confirm stays `FAIL:` with a note for a human, because an outside model downgrading findings would trade false positives for missed defects. Sends `git diff <base>...HEAD` minus sensitive files (80KB cap, never truncated) to `api.typesafe.ai`.
- **`scripts/plan-waves.mjs`** — **use when**: you need the parallel wave split of the open tasks (`/ccf:cook` step 2 runs it). **How to call**: `node "<plugin-root>/scripts/plan-waves.mjs" [--dir <path>] [--tasks a,b] [--jev]`; it prints JSON (`iteration`, `waves` of `{ id, title, taskFile, worktree, branch }`, `edges`, `unanswered`, `jev`) and always exits 0. Offline by default: code decides every edge (declared `Depends on`, file clash, no file list, unparseable path, shared hotspot). `--jev` with `TYPESAFE_API_KEY` set lets Jev add edges, never remove one. Read-only.
- **`scripts/worktree-preflight.mjs`** — **use when**: tasks ran in parallel (the `/ccf:cook` task agents, or one `claude -w ccf-<iteration>-<taskid>` session each), and their `worktree-ccf-*` branches are about to be merged. **How to call**: `node "<plugin-root>/scripts/worktree-preflight.mjs" [--dir <repo root>] [--into <ref, default HEAD>] [--branches a,b]`; it prints JSON (`ready`, `branches`, `pairs`, `problems`, `note`) and always exits 0. `ready: false` blocks the merge: `out-of-scope` (a real changed file outside the task's `Files to touch` and not a test; renames are not followed, so a moved file counts at both paths), `unparseable-declared` (a declared path with broken braces covers nothing), `actual-overlap`, `merge-conflict` / `pair-conflict` (read from `git merge-tree --write-tree`'s exit code, git >= 2.38), `unmatched-branch`, `duplicate-task`, `no-declared-files`, `git-error`. Read-only and offline (task 066); only committed work is visible. It does not merge or remove a worktree; `integrate-wave.mjs` does, and runs this script first.
- **`scripts/integrate-wave.mjs`** — **use when**: a wave's branches are ready to merge (`/ccf:cook` step 4d). **How to call**: `node "<plugin-root>/scripts/integrate-wave.mjs" [--dir <repo root>] [--branches a,b] --test "<test command>" --apply`; without `--apply` it only previews. It runs the preflight itself and refuses on `ready: false`, a dirty tracked tree or a missing `--test`; then `git merge --no-ff` per branch in order, the test command after EACH merge, and on red `git reset --hard` to the last green merge and stops. Only when all merges stay green does it `git worktree remove` (no `--force`) and `git branch -d` each branch. JSON out, always exit 0. No ledger (task 064 section 5 stays unbuilt).

## External judgment API (opt-in, NOT bundled)
- **TypeSafe Jev** — **use when**: you want an advisory second opinion on whether an in-review task's diff meets its acceptance criteria. **How to call**: not by hand. Set `TYPESAFE_API_KEY` (key from console.typesafe.ai/keys) in the environment and add `--completion-evidence` to the `completion-evidence.mjs` command in `hooks.json`; the Stop hook does the rest. The diff is sent to `api.typesafe.ai`, TypeSafe's docs say nothing about retention or training, so treat everything sent as leaving the machine. Docs give no size, rate or latency figures; measured live (task 057): 0.3 to 1.3s per request, HTTP 400 `max_tokens_exceeded` above about 33K input tokens (hence the 80KB cap), 400 questions per request accepted.

## Plugin development tools
- **Node ≥ 18** — runs the hooks and `bin/ccf-bootstrap.mjs`.
- **`tsc`** — type-checks JS via `tsconfig.json`. **Use when**: you just edited any `.mjs`. Run `npm install` (once) then **`npx -p typescript tsc --noEmit`** (bare `npx tsc` grabs an unrelated squat package since `typescript` isn't a devDependency). Needs `@types/node` (already in `devDependencies`) because `tsconfig` sets `"types": ["node"]` — this is a type-check devDependency, not a runtime dep.
- **`claude plugin` CLI** — `marketplace add` / `install`. **Use when**: installing locally or in `bin/ccf-bootstrap.mjs`.
- **`claude plugin eval`** (since 2.1.269; needs git >= 2.31) — **use when**: you change `ccf-spec-checker.md` or `check.md` and need to know whether review quality moved, not per commit (a full run costs about 6 USD). **How to call**: `cd plugins/ccf && env -u ANTHROPIC_API_KEY claude plugin eval . --scaffold --ablation none --allow-tools Bash --runs 3 --max-cost-usd 8 --no-publish --trust-plugin`. `env -u` because a stale `ANTHROPIC_API_KEY` beats the oauth login (401); `Bash` needs a working `bubblewrap` sandbox, and a nested container that cannot create loopback fails every Bash call, so run it on a host. Cases live in `plugins/ccf/evals/<case>/` (`case.yaml`, `prompt.md`, `scaffold.sh`, `graders/*.md`, where a `regex` grader's BODY is the pattern); results land in the git-ignored `evals/results/`. Baseline and case design: task 058.

## CCF self-checks (internal commands)
- `/ccf:check` — verify the implementation against this spec (conformance, conventions, SOLID, cross-check).
- `/ccf:updatespec` — refresh the spec after a session; **also records new tools with "when to use"** into this very file.
- `/ccf:cook` — **use when**: you want to run the WHOLE todo/in-progress backlog in one go — parallel waves (`plan-waves.mjs`), one `isolation: "worktree"` agent per task, each wave merged through `worktree-preflight.mjs` and `integrate-wave.mjs --apply` (tests after every merge; stop on any red), then a single `/ccf:check` and `/ccf:updatespec`. It commits on the current branch after one confirmation. **Mutually exclusive with `auto-verify.mjs --auto-verify`** — `/ccf:cook` drives the same verify step itself; don't enable both. NOTE: the contract-level test matrix (EP+BVA+decision-table) is designed and written directly during implement (part of the failing-test-first flow), NOT a separate command.

## Harness-supplied review/cleanup skills (observed, NOT CCF-shipped, both OPTIONAL extras)
Availability and SCOPE vary by harness — verify before relying on one. Neither is part of CCF's mandatory verify step (`/ccf:check` alone), so a missing one is never a skipped CCF gate — it is simply an extra the user chose not to run.
- **`simplify`** — **use when**: after implementing (this session or via `/ccf:cook`), you want quality cleanups (reuse, simplification, efficiency, altitude) on the working diff, beyond what `/ccf:check` looks for. **How to call**: Skill tool, no argument; it fans out 4 review angles then you apply the fixes. It WRITES files, so run it after `/ccf:check` has finished reading the diff. **Observed working** (cc-2.1.220-realign): its altitude angle correctly identified that a helper had been placed in the wrong domain module, and its efficiency angle measured a real 5x test-suite slowdown.
- **`code-review`** — **use when**: you want a SECOND, independent quality/correctness read of the change, in addition to the mandatory `ccf-spec-checker` review inside `/ccf:check`. **How to call**: Skill tool. It takes the **current working diff** when given no target, or a PR number / branch / path. Effort `low|medium|high|max|ultra` tunes breadth; **omitting the level reuses the last one typed** (v2.1.223). `--comment` posts findings as inline PR comments, `--fix` applies them to the working tree. Since v2.1.218 it runs as a **background subagent** (high/xhigh/max effort too since v2.1.232), so it returns an ack first and the findings later — never read the ack as the verdict ([[background-agent-result-is-instant-ack]]). Since v2.1.215 Claude no longer starts it on its own, so invoke it explicitly; v2.1.246 lets Claude self-start it again only on Bedrock, Vertex AI and Foundry (through the Claude apps gateway) or with telemetry or non-essential traffic disabled. Since v2.1.274 a model without tuned review settings gets lean inline review prompts instead of many review subagents. `/review` is an alias for it (v2.1.223), and `ultra` is a user-triggered, billed cloud review the main loop cannot launch for itself; its standalone form `/ultrareview` is called a cloud session since v2.1.274, and `/ultrareview --post` posts the PR comment directly when the findings arrive (v2.1.269).
  - **The old PR-only limitation is GONE.** Under cc-2.1.220 this skill read a diff only via `gh pr view`/`gh pr diff`, which is why closing task 049 required committing to a branch and opening a PR just to let it see the code. On the current build (v2.1.226, skill description verified in-session) a plain working diff is a first-class target, so **committing is no longer a precondition for using it**. Branch + PR remains a fine choice when the change deserves one; it is no longer a workaround. See [[slashcommand-tool-not-always-exposed]].

## Session task list (harness-supplied, not CCF-shipped)
- **`TaskCreate` / `TaskUpdate` / `TaskGet` / `TaskList`** — **use when**: a run has three or more distinct steps, or the user handed over a list of items, or progress needs to be visible while a long loop executes. In CCF that is `/ccf:cook` over a backlog (see `cook.md` step 2b), which matches every one of those triggers at once. **How to call**: `TaskCreate {subject, description, activeForm?}` (every task is born `pending`); `TaskUpdate {taskId, status}` walking `pending → in_progress → completed` (`deleted` removes one), plus `addBlockedBy`/`addBlocks` for dependency edges and `owner` to claim; `TaskList` to enumerate `id`/`subject`/`status`/`owner`/`blockedBy`. Schemas may be deferred — load them with `ToolSearch` before the first call.
  - **`TodoWrite` is the OLD tool and is disabled by default.** Since Claude Code v2.1.142 (TS Agent SDK 0.3.142) sessions use the structured `Task*` tools instead; `TodoWrite` returns only under `CLAUDE_CODE_ENABLE_TASKS=0`. Never write `TodoWrite` into a CCF prompt.
  - **NOT the `Task` spawn tool.** `Task` (a.k.a. `Agent`) spawns a subagent; `TaskCreate`/`TaskUpdate`/`TaskList` manage a checklist. The shared prefix is a naming collision, nothing more — do not reason from one to the other.
  - **Ephemeral, and therefore never a replacement for `PLAN.md`.** The list is scoped to the current coding session, so it cannot carry status across sessions. `.claude/plan/PLAN.md` stays the source of truth, and the two lifecycles are deliberately different (`completed` in the list vs `in-review` in `PLAN.md`) — only `/ccf:updatespec` writes `done`.
  - **Availability is not guaranteed** — treat a missing `Task*` tool exactly like a missing `/code-review`: say so explicitly and carry on from `PLAN.md`, never silently skip the tracking and imply it happened.
  - **Untested against an agent denylist**: all 5 CCF agents declare `disallowedTools: Agent, Task`. Whether that exact-match string also blocks `TaskCreate` has NOT been observed. It does not matter today because only the main-loop command `cook.md` uses these tools, never the task agents it spawns — do not add them to an agent on the assumption that it works.

## Optional official Claude Code commands (runtime, not CCF-shipped)
These are official Claude Code slash commands, NOT part of CCF's artifact count (no command/agent/hook/skill added) — they may be ABSENT on an older Claude Code build, so treat them as optional enhancements, never a required step.
- **/advisor** — **use when**: you want a DIFFERENT model to sanity-check an implementation alongside the mandatory same-model `ccf-spec-checker` review (`check.md` closing). **How to call**: `/advisor sonnet` or `/advisor fable` (also accepts `opus`, a specific model ID, or no argument to open a picker); the choice persists in user settings. It is a SUPPLEMENT — it never replaces `/ccf:check`'s mandatory `ccf-spec-checker` review, which stays the single required verify step before `/ccf:updatespec` marks a task `done`. Note: `/ccf:plan` no longer runs a mandatory plan-time `ccf-spec-checker` review to supplement — that premortem loop was retired along with the coding subagent (see `architecture.md`); `/advisor` on a plan is now a purely optional sanity-check, not a supplement to any enforced gate.
- **/goal** — **use when**: running `/ccf:cook` over a backlog and you want the session to keep working autonomously until a condition holds (e.g. "all selected tasks are in-review"), instead of re-prompting after every turn. **How to call**: `/goal <condition>` (a fast model checks the condition after each turn; `/goal clear` — or aliases `stop`/`off`/`reset`/`none`/`cancel` — removes it). It is a SECONDARY convenience only — it never replaces `/ccf:cook`'s stop-on-red-gate law (a RED gate still stops the loop immediately).
  - **Observed behavior (cc-2.1.220-realign), state it when advising a user:** the Stop hook re-blocks on EVERY stop until the condition holds, and its checker reads the literal condition. A condition naming a whole command (`/goal /ccf:cook`) is therefore only satisfied when that command's LAST step completes — so an externally blocked step (denied permission, an unavailable `/ccf:check`) makes the goal unsatisfiable and the session loops on advisory text without progressing. When that happens: say plainly that the condition cannot be met, name the exact blocker, stop taking action, and tell the user to run `/goal clear` or remove the blocker. Prefer phrasing a goal as an OBSERVABLE END STATE ("all selected tasks are in-review") over a command name.

## Convention for adding a new tool
When integrating a new tool/MCP, add an entry here in the format "**name** — when to use — how to call", and update the `allowed-tools` of the related COMMANDS (main-loop scope, least-privilege). Do NOT add it to an agent `tools` list: subagents have NO `tools` allowlist — all 5 CCF agents reach project-arbitrary MCP by INHERITANCE (`disallowedTools: Write, Edit, NotebookEdit, Agent, Task` → inherit-all-minus-file-writes-minus-spawn), so a newly added project MCP is automatically available to them with no per-agent edit. An inherited MCP tool may be lazily loaded — load its schema with `ToolSearch` before calling it (a blind call fails with InputValidationError).
