# Architecture

## Artifact types (don't confuse their roles)
1. **Command** (`plugins/ccf/commands/*.md`) — a prompt that drives Claude in the **main conversation** when the user types `/ccf:<name>`. NOT a script. Has frontmatter (`description`, `argument-hint`, `allowed-tools`, `model`).
2. **Agent / subagent** (`plugins/ccf/agents/*.md`) — a READ-ONLY prompt that runs in a **separate** context when delegated via Task, used for discovery, review or best-practice grounding, never for writing code (see "Command ↔ agent boundary" below). Has frontmatter (`name`, `description`, `model`, optional `effort` = reasoning depth; tool access is by INHERITANCE, not a `tools` allowlist — see "Agent context & rule propagation").
3. **Hook** (`plugins/ccf/hooks/*.mjs`) — executable Node code run out-of-process, called by Claude Code at lifecycle events. This is the ONLY deterministic part; everything else is a prompt.
4. **Skill** (`plugins/ccf/skills/<name>/SKILL.md`) — a prompt in its own folder, auto-discovered. Two kinds: an **internal building block** invoked BY a command via the Skill tool (`grill-me`, `user-invocable: false`, holds a shared procedure so it isn't duplicated), and a **user-facing workflow skill** (`plan`), typed as `/ccf:<name>` exactly like a command (docs: commands and skills are merged, same capability) and also loadable by the model through its `description`. See `@.claude/rules/components.md`.
5. **Script** (`plugins/ccf/scripts/*.mjs`) — a CLI tool a HUMAN runs (`node <abs-path>/archive-plan.mjs --apply`). Same no-build/no-dependency/Windows-clean rules as a hook, and it may reuse `hooks/lib/*`, but it is NOT event-driven: nothing invokes it automatically. **Use a script, not a hook, when the action MUTATES the user's files** (rewrites the plan, moves history, touches git). A hook fires with no human in the loop, so a wrong detection there silently rewrites the project; a script's blast radius is bounded by someone choosing to run it. The paired hook then does only the DETECTION half and nudges — see `archive-plan.mjs` + `updatespec-nudge` clause (D), and `prune-archive.mjs` + clause (E). Currently **9** scripts (`archive-plan.mjs`, `prune-archive.mjs` and `integrate-wave.mjs` mutate files, the second merging a wave's worktree branches only after its own preflight run and removing worktrees only when the merged tests stay green; `plan-waves.mjs` is read-only and prints the wave split `/ccf:cook` runs; `jev-slice-check.mjs`, `jev-verify-findings.mjs` and `jev-backtest.mjs` mutate nothing but call a paid external API, so a person chooses when to run them — the same "a human, not an event, decides" reason; `worktree-preflight.mjs` is read-only and offline, and is a script because it gates a merge only a person starts; `memory-audit.mjs` is read-only, with an opt-in `--jev` network call). Three commands call scripts on the user's behalf: `/ccf:check` step 6b runs `jev-verify-findings.mjs` when a `FAIL:` exists and `TYPESAFE_API_KEY` is set (setting that key is the human opt-in, and the step says in one sentence that the diff leaves the machine), `/ccf:updatespec` runs `memory-audit.mjs` (step 5b) and `prune-archive.mjs` (step 6, `--apply` only after the user agrees), and `/ccf:cook` runs `plan-waves.mjs`, `worktree-preflight.mjs` and `integrate-wave.mjs --apply` after the user confirms the run's commits once. Add it to `tsconfig.json`'s `include`; `package.json`'s `files` already ships `plugins`, so no packaging change is needed.

## Command ↔ agent boundary (CCF law)
- **Writer agents exist ONLY inside a worktree the harness isolates.** `/ccf:cook` step 4a spawns one built-in `general-purpose` agent per task of a wave, all in one message, each with `isolation: "worktree"`, so every writer has its own checkout and none writes the main checkout. The parallel gain is why they came back (task 064 had rejected them); the isolation, the mandatory `worktree-preflight.mjs` gate and the tests `integrate-wave.mjs` runs after every merge are what make it safe. `/ccf:plan` step 6 still implements a single task directly in the main session. **Observed on 2.1.285:** a subagent cannot use `EnterWorktree`/`ExitWorktree` (`name` and `ExitWorktree` are refused, and after `EnterWorktree(path)` Bash refuses to run), and the isolation worktree starts at `origin/<default-branch>`, so the agent creates its task branch with `git switch -c <branch> <base>`.
- **Every CCF agent is read-only**, used only when: (a) discovery/research can fan out in parallel (5 `ccf-codebase-analyzer` — in `/ccf:init` B1 on the agent's **set A** onboarding slices, and in `/ccf:plan` step 1b on its **set B** planning slices; `ccf-best-practice-researcher` for grounding a decision), or (b) a fresh, isolated context reviews finished work more sharply than the context that wrote it (`ccf-spec-checker` plus the scope-only `ccf-scope-checker`, spawned in parallel by `/ccf:check` with non-overlapping scopes and merged by `file:line`) or drafts spec prose for the main thread to write (`ccf-spec-writer` in `/ccf:updatespec`). None of them writes application code; only the worktree-isolated task agents above do.
- **CCF commands do codebase discovery through `ccf-codebase-analyzer`, never through the built-in `Explore` agent.** Both are read-only fan-out, so the reason is not safety: CCF does not OWN `Explore`'s prompt (it is a harness artifact, which is why `explore-guide-inject` has to inject guidance at spawn from the outside), so it cannot be told what a CCF planner needs, cannot be given a fixed report shape, and cannot be made to return a mandatory **Unknowns** section. `Explore` remains fine for ad-hoc searching the user or the model initiates; it is the COMMANDS that must not rely on it.
- **Do NOT spawn multiple agents in parallel that touch overlapping ground.** For writers this is enforced in code: `plan-waves.mjs` puts two tasks in one wave only when no declared dependency, file clash, missing file list or shared hotspot links them, and Jev may only add edges. NOTE: since subagents now inherit the project's MCP, a read-only agent CAN reach a project DB MCP and (rarely) issue a write through it — that is permission-gated (each MCP call prompts) and the body mandates SELECT/read-only, so parallel read-only research stays safe; treat a parallel DB-write via project MCP as the rare, prompt-gated exception, not the norm.
- **Slice granularity (right-size, not micro-size):** each task agent (or the main session in `/ccf:plan` step 6) implements exactly one task, and a task is a COHESIVE PR-sized vertical slice — not a fragment. Split a slice smaller only on a real driver (data dependency, an independent green gate, risk isolation = refactor separated from feature, or it won't fit one context/review); otherwise fold doc/spec/count-sync into the feature task. This sizes the WORK UNIT one agent implements; parallelism comes from waves of such units, never from splitting one task. See the `plan` skill's step 4.

## Deterministic part vs prompt part
- Logic that must be certain (e.g. "block `/ccf:plan` if not in plan mode") → goes in a **hook** (`plan-mode-guard.mjs`), because a prompt can be ignored by the model. That guard only sees a TYPED `/ccf:plan`: a model-initiated Skill call to `plan` bypasses `UserPromptSubmit`, so on that path the skill's own step 0 is the only check. The command still keeps a verbal backup layer (see the `plan` skill's section 0) — this is deliberate defense-in-depth, not redundant duplication.
- Likewise the opt-in `auto-verify.mjs` (`Stop`) makes the verify step DETERMINISTIC: rather than trusting the model to remember to run `/ccf:check` before stopping, it BLOCKS the stop (`decision:"block"`, the "ralph loop") and feeds `/ccf:check` then `/ccf:updatespec` back as the next instruction — but only when enabled and there is real work to verify. See `@.claude/rules/hooks.md`.
- Judgment/interpretation logic → goes in the **command/agent prompt**.
- `ccf-spec-checker`'s review is such judgment work: conformance, conventions, SOLID/OOP, drift and cross-check all require reading and weighing code against a spec, not a mechanical check — review depth lives in the agent prompt, not in any hook.

## Agent context & rule propagation
- An **output style** modifies the MAIN loop's system prompt and is NOT inherited by spawned subagents — there is no built-in style→subagent propagation ([#8395](https://github.com/anthropics/claude-code/issues/8395)). A subagent gets its OWN system prompt.
- A subagent DOES auto-load the **memory hierarchy** (`.claude/rules/*` + CLAUDE.md, via `@import`). So **enforceable coding rules belong in `.claude/rules`**, never in an output style alone — only `.claude/rules` reaches the subagent. That is also how a `/ccf:cook` task agent gets the coding rules, backed by its brief telling it to read them; CCF still runs no spawn-time rules-injection hook.
- The one remaining `SubagentStart` hook, `explore-guide-inject` (matcher `"Explore"`), uses the spawn-time `additionalContext` lever for a DIFFERENT purpose: CCF does not own the built-in `Explore` subagent's prompt (a harness artifact), so this hook injects a language-agnostic, LSP-conditional directive (prefer the `LSP` tool's semantic navigation + ripgrep `Grep` + `Glob` over reading whole files). It is best-effort and never blocks a spawn. See `@.claude/rules/hooks.md`.
- **Tool / MCP / skill inheritance** (grounded `code.claude.com/docs/en/sub-agents` + `/en/tools-reference`): a subagent that OMITS `tools` inherits ALL the main loop's tools — every project MCP server + the Skill tool; one with `disallowedTools` inherits-all-MINUS the listed file-write tools. A `tools` allowlist instead BLOCKS unlisted MCP + Skill, and a plugin subagent's `mcpServers`/`permissionMode`/`hooks` are "Ignored for plugin subagents" — so inheritance (omit / `disallowedTools`) is the ONLY way a subagent reaches arbitrary project MCP. **Nested spawn (grounded, `code.claude.com/docs/en/sub-agents` + `/agent-sdk/subagents` + changelog): a subagent CAN spawn nested subagents — the `Agent`/`Task` tool is INHERITED like any other tool, not blocked by default. The limit is VERSION-DEPENDENT, not fixed: 5 in v2.1.172 through v2.1.216, 1 in v2.1.217/v2.1.218, and back to 3 from v2.1.219 onward (the default as of this writing), configurable via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (setting it to 1 disables NESTED spawning only — it does NOT disable subagents; the harness still spawns depth-1 agents normally).** CCF blocks it deterministically via `disallowedTools: Agent, Task` on all 5 agents (a leaf-agent invariant — no CCF agent spawns another); an inherited MCP tool may be lazily loaded → use `ToolSearch` before calling. All 5 CCF agents are read-only: inherit-all-minus-file-writes-minus-spawn (`disallowedTools: Write, Edit, NotebookEdit, Agent, Task`).
- **Background-by-default (per changelog; OBSERVED 2026-10-01, and `run_in_background: false` did NOT prevent it):** since Claude Code 2.1.198 a spawned subagent runs in the BACKGROUND by default, and v2.1.232 states it for every non-teammate agent spawn in an interactive session (the same release turned `subagent_type: "fork"` on by default). There is no agent-frontmatter lever to force it synchronous — `background: true` forces IN, but a `false` value is not a documented behavior. CCF makes every spawn it must wait on synchronous with `run_in_background: false` written explicitly at the CALL SITE. The literal appears on **8 lines** across the 4 command files and the `plan` skill (`skills/plan/SKILL.md` 2, `init.md` 3, `check.md` 1, `cook.md` 1, `updatespec.md` 1). Verify with `grep -c 'run_in_background: false' plugins/ccf/commands/*.md plugins/ccf/skills/plan/SKILL.md`, summed across the files. In the task-073 session all 7 spawns (5 analyzers, 2 checkers) passed it and still returned the async ack, so the literal is necessary but not sufficient: every caller must also wait for each completion notification before using a report.
- **No hook-level gate yet.** Nothing in `hooks/*.mjs` currently blocks or detects a background spawn deterministically. Task 039 concluded this is buildable for the read-only research/review spawns that remain, but it was DEFERRED to task 042.
- **A plugin agent inherits the PARENT SESSION's permission mode.** Real observation from an earlier session, while CCF still had a writer subagent: every spawn was blocked from writing a path the parent session's own permission had blocked, and once the parent's permission opened, the spawned agent could write there too. This is a live confirmation (not just a changelog citation) that a subagent does not carry its own independent permission grant. It is why `plan-mode-guard` gates the PARENT prompt rather than trying to gate a subagent directly — permission state flows from the parent down, not the reverse — and it remains true for any future subagent CCF might add.

## Distribution flow
`bin/ccf-bootstrap.mjs` (npx) → `claude plugin marketplace add` + `install` → Claude Code reads `.claude-plugin/marketplace.json` → points to `plugins/ccf` → reads `.claude-plugin/plugin.json` → loads commands/agents/skills/.mcp.json **and** `hooks/hooks.json`, all auto-discovered by their standard location. Do NOT add a `"hooks"` field pointing at `hooks/hooks.json` in `plugin.json` — that re-loads the already-auto-loaded file and fails with `Duplicate hooks file detected`. The `manifest.hooks` field is only for *additional* hook files at a non-standard path. See `@.claude/rules/hooks.md`.

## Invariants
- Every command name in docs/prompts must match a real file in `commands/`. There are currently **4** commands, **5** agents (all read-only) and **2** skills (`plan`, the workflow behind `/ccf:plan`; internal `grill-me`) — keep README/MEMORY in sync; the real files in `commands/`+`agents/`+`skills/` are the source of truth.
- Components reference each other by name (e.g. `/ccf:check` calls the `ccf-spec-checker` agent); renaming a file ⇒ update every reference.
