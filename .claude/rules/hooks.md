# Hooks (`plugins/ccf/hooks/*.mjs`)

## Absolute invariants
- **No-build, no-dependency, Windows-clean.** Hooks are `.mjs` ESM run directly with `node` (Node ≥ 18). Do NOT add an npm dependency, do NOT add a transpile/bundle step. All I/O via `node:fs`, `node:path`, `node:child_process` built-ins.
- Type-check with `tsc` using `checkJs` + JSDoc (see `tsconfig.json`). Do NOT switch to `.ts`.
- Paths in `hooks.json` use `node "${CLAUDE_PLUGIN_ROOT}/hooks/<file>.mjs"` — this variable ONLY expands in a hook command.

## I/O contract (packaged in `hooks/lib/io.mjs` — reuse it, don't rewrite)
- **Read stdin**: `readStdinJson()` — always returns `{}` on empty/TTY/parse error so the hook NEVER crashes.
- **Inject context (non-blocking)**: `emitContext(eventName, text)` — prints `{ hookSpecificOutput: { hookEventName, additionalContext } }` then `exit 0`. ONLY for events whose schema accepts `additionalContext`: SessionStart, UserPromptSubmit, PostToolUse, **SubagentStart** (the latter adds the string to the spawned subagent's context before its first prompt; cannot block the spawn) and, per the Claude Code 2.1.163 changelog, **Stop and SubagentStop as well** (NOT YET OBSERVED live on this project's harness — see project memory `subagentstop-shape-unconfirmed`).
- **Advise at Stop (non-blocking, single-channel — the shipped default)**: `emitSystemMessage(text)` — prints `{ systemMessage }` then `exit 0`. The non-blocking channel for a `Stop` hook (omitting `decision` lets the stop proceed; a `decision: "block"` would force Claude to keep working). This stays the DEFAULT path for `updatespec-nudge.mjs` — see `emitStopAdvisory` below for the opt-in dual-channel sibling.
- **Block at Stop (the "ralph loop")**: `blockStop(reason, systemMessage)` — prints `{ decision: "block", reason, systemMessage }` then `exit 0` (the block is carried by the JSON, NOT an exit code — Stop is the inverse of UserPromptSubmit where exit 2 blocks). `decision:"block"` forces Claude to keep working and feeds `reason` back as the next instruction; the optional `systemMessage` shows the user why. Used by the opt-in `auto-verify.mjs` to drive the verify step. The opposite of `emitSystemMessage` (advisory).
- **Block a prompt**: `blockUserPrompt(reason)` — writes `reason` to stderr then `exit 2`. UserPromptSubmit only.
- **Advise at Stop, dual-channel (non-blocking, OPT-IN)**: `emitStopAdvisory(context, message)` — prints the COMBINED `{ hookSpecificOutput: { hookEventName: "Stop", additionalContext }, systemMessage }` payload then `exit 0`, so one emit reaches BOTH the model and the user. Per the 2.1.163 changelog, Stop's schema now accepts `additionalContext` — NOT YET OBSERVED live on this project's harness. `updatespec-nudge.mjs` picks the channel with an opt-in `--dual-channel-stop` argv flag: ABSENT (the shipped `hooks.json` state) → `emitSystemMessage` (single-channel, the INVARIANT default that must not change); PRESENT → `emitStopAdvisory`. Same caution level as the `034a` observation gate — stay single-channel until a real post-reload payload confirms the dual shape actually reaches the model.
- **`blockSubagentStop` and `denyTool` were removed** (this iteration, alongside `plan-review-gate.mjs` and `implementer-verify-gate.mjs` below): both had exactly one caller each, and both callers are gone now that CCF has no PreToolUse gate and no SubagentStop gate. If a future hook needs to block a SubagentStop or deny a PreToolUse tool call, re-add the matching helper then, following the same narrow, single-purpose shape as its sibling `blockStop`/`blockUserPrompt` — do not resurrect unused code speculatively. `emitPromptWarning` (and the private `buildDualChannelPayload` it shared with `emitStopAdvisory`) went the same way when `context-guard.mjs` was retired.

## Exit code semantics (per Claude Code docs)
- `exit 0` — no decision, the flow continues normally (even after emitting additionalContext).
- `exit 2` — **BLOCK**; stderr is sent back as feedback. This is the only blocking mechanism CCF uses.
- `exit 1` — non-blocking error, does NOT block. CCF avoids it (it adds noise without blocking).

## Events CCF currently uses (`hooks.json`)
- `UserPromptSubmit` → `plan-mode-guard.mjs`: only intervenes on prompts matching `/(^|\s)\/ccf:plan(\s|$)/` — the namespaced form only; bare `/plan` is Claude Code's own built-in plan command and must NOT trigger this guard. Blocks if `permission_mode !== "plan"`. Every other prompt `exit 0` immediately.
- `UserPromptSubmit` → `plan-skill-inject.mjs` (second object in the same array): bare `/plan` is Claude Code's BUILT-IN, so a plugin skill can never take that name (plugin skills are always `/ccf:<name>`); plan mode itself is therefore the trigger. When `permission_mode === "plan"`, the project has a `.claude/plan` directory, and the prompt is not a leading `/ccf:` command, it calls `emitContext("UserPromptSubmit", buildPlanSkillDirective())` telling the model to invoke the `ccf:plan` skill (a pure question about the code is answered directly instead). At most ONE nudge per `session_id`, held by a 1-byte marker file in the OS temp dir (never cleaned up on purpose: the OS reclaims temp, and a cleanup hook would add a second moving part); no `session_id`, an unwritable marker, or a `Skill` tool call / typed `/ccf:plan` already in the transcript all mean silence. Decision logic is the pure `lib/plan-trigger.mjs` (`shouldInjectPlanSkill` requires the literal `true`/`false` per flag, so a missing signal reads as "do not nudge"). Never blocks; ANY error `exit 0`. **NOT YET OBSERVED live** whether the built-in `/plan <text>` reaches this hook at all (task 053); the skill `description` is the backup for that case. Removing its `hooks.json` entry turns the behavior off.
- `SessionStart` (matcher `startup|clear|compact`) → `session-start.mjs`: injects the context-first reminder; if CCF-managed, adds a freshness signal + re-loads the active task (in-progress OR in-review, via `findActiveTask`) after `compact`/`clear`.
  - **Freshness signal** (`lib/freshness.mjs`, shared with `updatespec-nudge.mjs`): the PRIMARY signal is git **committer time** (`git log -1 --format=%ct -- <pathspec>` via `spawnSync`, `shell:false` + `encoding:"utf8"`) of the last commit touching code vs spec — NOT mtime, because ordinary git ops (`checkout`/`pull`/`clone`/even a `commit` that touches a code file last) rewrite mtime to "now" regardless of content, which caused a false "spec older than code" nudge. The pure `decideFreshness` only nudges when BOTH git times resolve and `codeGit > specGit`; a `null` git time on either side (not a git repo, git missing, or a path with no commits) **falls back to the depth-limited mtime walk** (`newestMtime`), so freshly-`/ccf:init`-ed non-git projects still work. Best-effort, advisory only, never throws (`gitCommitTime` returns `null` on any error/empty stdout). Decision logic is pure + unit-tested (`lib/freshness.test.mjs`).
- `Stop` → `updatespec-nudge.mjs`: PURELY ADVISORY, never blocks. Surfaces nudges via `emitSystemMessage` (`{ systemMessage }`), NOT `additionalContext` (which `Stop` does not support). Must check `input.stop_hook_active` to avoid loops. Composes **four INDEPENDENT clauses** into the single non-blocking Stop channel (none gates another; all off → emit nothing): **(A) verify-work** — if this SESSION edited a code file but ran no test command (SESSION evidence read best-effort from `transcript_path` via `lib/verify-trace.mjs`: pure `needsVerifyNudge` + the defensive `readTranscriptSignals`/`editedAnyCodeFile`/`isTestCommand` helpers, all unit-tested, never throw), nudge to run the tests/type-check before stopping; **(B) updatespec** — if `specsOlderThanCode` (spec-vs-code staleness across git history, `lib/freshness.mjs`), nudge `/ccf:check` then `/ccf:updatespec`; **(C) plan-status-sync** — if this SESSION ran `git commit` (`lib/git-trace.mjs` `committedThisSession`, the SAME role-gated assistant-`tool_use` shell scan as verify-trace, matching `/\bgit\s+commit\b/`) AND `lib/plan.mjs` `findNonDoneTasks` finds PLAN.md rows still OPEN (todo/in-progress/in-review/blocked/anything else — `done` and a deliberately-abandoned status like `dropped`/`cancelled`/`won't-fix` both count as CLOSED, per `CLOSED_STATUS_RE`), nudge to mark each `done` only after its `/ccf:check` passes, or fix its status; **(D) archive-plan** — if `lib/archive.mjs#findRetirableIterationsIn` finds an iteration in PLAN.md whose EVERY task row is closed, nudge to retire it by running `scripts/archive-plan.mjs` (the command string carries an ABSOLUTE path resolved from `import.meta.url`, not from `cwd`, because the plugin runs from its installed cache copy — a cwd-relative path would not exist there). Clause D DETECTS only: the retirement rewrites PLAN.md + ARCHIVE.md and moves task files, so the mutation is deliberately left to the human-run script (detection-vs-action split: the hook is certain about the fact, the human owns the mutation). `findNonDoneTasks`/`findActiveTask` resolve the STATUS column **dynamically** from each table's header row (shared `collectTaskRows`), not by assuming it is always the last cell — a real-world PLAN.md that puts another column (e.g. `Predecessor`) after `Status` would otherwise misread that column's value as the status, making every row look "not done" (a real dogfood finding, fixed). `collectTaskRows` ALSO strips markdown emphasis from the status cell (`stripEmphasis`: outer runs of `*`, `_`, backtick, whitespace) before anything interprets it — a SECOND real dogfood finding of the same family: this repo's own PLAN.md wrote `| 036 | … | **done** |` to visually stress the status, and because every status predicate here is anchored (`^done$`, `^in-review$`), the decoration made two finished tasks read as OPEN and clause C named them as unfinished. Emphasis is presentation, not data. Deliberately applied to the status cell ONLY: it is the sole field compared against anchored predicates, while id/title are just displayed. **PLAN.md is also trimmed to the CURRENT iteration** (closed iterations move to `.claude/plan/ARCHIVE.md`, which NO hook reads) — so a closed row left behind in PLAN.md is the other way this count goes wrong, and `/ccf:updatespec` owns that retirement step. The verify-work + plan-status-sync signals key on the HARNESS-DEPENDENT shell-tool name (`bash`/`shell`/`powershell`/`pwsh`) — the `SHELL_TOOL_NAMES` set is COPIED into `git-trace.mjs` (it is module-private in `verify-trace.mjs`, not imported cross-file) — and the harness-dependent edit-tool shape, kept broad so a Windows/PowerShell session or a `MultiEdit` is not a missed signal; both transcript scans are ROLE-GATED to `assistant` lines so user prose ("i will git commit") never false-positives. Despite the filename, the hook is the general CCF Stop nudge, not only the updatespec one. This hook is PURELY ADVISORY — the blocking Stop behavior lives in the separate opt-in `auto-verify.mjs`. **Channel is opt-in dual (task cc-2.1.220-realign):** the default (shipped `hooks.json`, no flag) path calls `io.mjs#emitSystemMessage` — user-facing only, this single-channel behavior is an INVARIANT that must not silently change. Adding `--dual-channel-stop` to its `hooks.json` command switches every clause to `io.mjs#emitStopAdvisory` instead — the SAME advisories, but also relayed to the model via `additionalContext` (per the 2.1.163 changelog's Stop support, NOT YET OBSERVED live on this harness) so the model can restate them `RELAY_IN_USER_LANGUAGE`. The flag is NOT present in the shipped `hooks.json` — default OFF, same caution as the `034a` observation gate.
- `Stop` → `auto-verify.mjs` (a SECOND object in the `Stop` array, alongside `updatespec-nudge.mjs`): OPT-IN and the ONLY CCF Stop hook that can BLOCK. Uses the grounded "ralph loop" (`io.mjs#blockStop` → `{ decision:"block", reason, systemMessage }`) to drive the main loop through a **single verify step** when there is work to verify. **Opt-in by arg**: it fires only when its `hooks.json` command carries `--auto-verify` (no arg → `exit 0` silently, default OFF — the same toggle pattern as `updatespec-nudge`'s `--dual-channel-stop`; the hooks.json entry IS the toggle). The drive decision is the pure `lib/verify-chain.mjs#shouldDriveVerify({ enabled, stopHookActive, hasInReviewTask, editedCodeThisSession, checkAlreadyRan })` = `enabled && !stopHookActive && hasInReviewTask && editedCodeThisSession && !checkAlreadyRan`. The five signals REUSE the existing tested helpers (no re-implementation): `enabled` ← `--auto-verify` in argv; `stopHookActive` ← `input.stop_hook_active` (the within-drive loop guard); `hasInReviewTask` ← `lib/plan.mjs#findActiveTask` ≠ null (the trigger — an in-progress/in-review task); `editedCodeThisSession` ← `lib/verify-trace.mjs#readTranscriptSignals().editedCode` (anti-plan-only guard); `checkAlreadyRan` ← `lib/review-trace.mjs#hasSpecCheckerSpawn(parseJsonl(...))` (the cross-Stop guard, satisfied once `/ccf:check` has spawned `ccf-spec-checker`). When true → `blockStop(buildVerifyReason({ disciplineOn: readDisciplineOn(rulesDir) }), <short systemMessage>)`. `buildVerifyReason` names a SINGLE step, not a multi-gate pipeline: run `/ccf:check` (which runs the tests itself, and confirms the contract-level matrix tests too when `readDisciplineOn` finds the "Test design discipline" block + `Matrix required: yes` in `testing.md`), then `/ccf:updatespec` once it comes back clean (no `FAIL:` finding, the review-marker vocabulary defined in `.claude/rules/prompt-standard.md`); any `FAIL:` → STOP + tell the user, do NOT mark done. There is no separate `/code-review` step in this mandatory chain — it stays a good optional extra the user can run by hand. `shouldDriveVerify`/`readDisciplineOn`/`buildVerifyReason` are pure + unit-tested (`lib/verify-chain.test.mjs`); the hook is I/O only. **Loop-guard tradeoff (accepted, and NOT harmless — say so plainly):** `stopHookActive` guards re-entry within ONE drive, and `checkAlreadyRan` is the cross-Stop guard, but `checkAlreadyRan` only proves a SPAWN, not a FINISHED review (see `hasSpecCheckerSpawn`'s own note) — a `ccf-spec-checker` that was spawned but has NOT yet returned (background-by-default since 2.1.198) still reads as `checkAlreadyRan = true`, which SUPPRESSES the verify drive for the rest of this Stop. This is accepted because the hook defaults OFF and the advisory `updatespec-nudge.mjs` layer still nudges independently — but it is a real false-negative, not a cosmetic one; do not describe it as harmless. Best-effort: ANY error → `exit 0` (never break a session). Prompt backup: the verify step is also the documented CCF workflow.
  - **The `Stop` array now holds THREE hooks**: `updatespec-nudge` (default ADVISORY single-channel — `emitSystemMessage`; opt-in dual-channel — `emitStopAdvisory`, only when `--dual-channel-stop` is set — never blocks either way), `auto-verify` (OPT-IN BLOCKING — `blockStop`, only when `--auto-verify` is set) and `completion-evidence` (OPT-IN ADVISORY, below).
- `Stop` → `completion-evidence.mjs` (third object in the `Stop` array): the FIRST hook that calls the network, so its rules are stricter than the others. Opt-in by TWO switches: `--completion-evidence` in its `hooks.json` command (absent in the shipped file) AND `TYPESAFE_API_KEY` in the environment (never argv, never printed). It asks Jev (TypeSafe System One, `POST /v1/systemone`) one Noul per acceptance criterion of the `in-review` task plus a scope-creep Noul, with the task, `git diff HEAD` + untracked files and the last test output as `state`, and prints the criteria below the 0.5 threshold via `emitSystemMessage`. **The diff leaves the machine:** `lib/completion-evidence.mjs` strips sensitive file names (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `.npmrc`, `.netrc`, `settings*.json`, `*credential*`, `*secret*`, anything under `secrets/`; a diff header it cannot parse is dropped too, fail-closed) and does NOT send an over-80KB payload and does not truncate it (a cut diff makes Jev judge code it cannot see); it says once that the diff was not checked, because silence would read as a pass. Runs only with exactly ONE in-review task (several is ambiguous, so it stays silent), code edited this session and `stop_hook_active` false; one question per task id + diff hash (a temp-dir marker written BEFORE the call, so a failing API is not retried on every Stop; HTTP 400 gets the same one-time "not checked" notice as an oversize diff). Every other failure (no key, 401/422/429/529, bad JSON, timeout, not a git repo, unwritable marker) exits 0 silently; `fetch` aborts at ~6.5s because the harness kills a hook at 10s (exit 1, nothing reported). `lib/jev-client.mjs` takes `fetch` as a parameter so the error surface is unit-tested; `io.test.mjs` runs the real hook against a `node:http` fake on 127.0.0.1 (`CCF_JEV_URL`, `CCF_JEV_TIMEOUT_MS` are test seams). Measured live (task 057, repo copy of the hook + real key, NOT the installed plugin cache and NOT inside a real Stop event): 0.3 to 1.3s per request; HTTP 400 `max_tokens_exceeded` above about 33K input tokens (110KB of source passes, 120KB fails), hence the 80KB cap; 400 questions per request accepted. On 28 hand-labelled criteria plus 8 injected defects the 0.5 threshold flagged 12/13 unmet claims and 6/8 defects with 1 false alarm on 23 correct ones; 0.6 catches one more unmet claim (13/13) at the same false-alarm count, a one-item gap on a hand-made set, so 0.5 stays rather than tuning to 28 cases. Weak spots seen: a one-token edit inside a longer expression, and criteria the diff alone cannot show. A multi-task working tree (122KB here) exceeds the cap, so run it per task.
- **CCF no longer runs a `context-guard` hook** (retired 2026-09-29 by explicit user command, with `lib/context-usage.mjs`): the proactive-`/compact` nudge measured context from the undocumented transcript `.jsonl` and needed a hand-maintained model-window list that already mis-sized a new family once. `UserPromptSubmit` now holds `plan-mode-guard` and `plan-skill-inject`, neither of which measures context. Do not re-add a compact suggestion unless the user asks for one.
- `SubagentStart` (matcher `"Explore"` — the ONLY hook in this event array) → `explore-guide-inject.mjs`: injects a short, **language-agnostic, LSP-conditional** exploration directive into the built-in `Explore` subagent so it prefers SEMANTIC navigation (the `LSP` tool — `workspaceSymbol`/`goToDefinition`/`findReferences`/`documentSymbol`, with "no server → just fall back, don't retry") + ripgrep-backed `Grep` + `Glob` over reading whole files. CCF does NOT own the `Explore` agent's prompt (it is a harness artifact), so injecting context at spawn via `additionalContext` is the only deterministic lever. The hooks.json `"Explore"` matcher IS the gate; an accidental over-match only adds harmless LSP guidance. Content lives in the pure `lib/explore-guide.mjs` (`buildExploreGuidance`, unit-tested); the hook is I/O only. Best-effort: ANY error → `exit 0` (we MUST never block a spawn).
  - **CCF no longer runs an `agent-rules-inject` hook** (removed this iteration, alongside the `ccf-implementer` agent it targeted): since every CCF agent is now read-only and none of them writes code, there is no writer subagent whose adherence to the coding rules needs reinforcing at spawn via `additionalContext` — the main loop, which does all the writing, already has `.claude/rules` and the active output style loaded natively. The `SubagentStart` array now holds exactly ONE hook, `explore-guide-inject`, matcher-gated to `"Explore"` only.
- **Background-spawn observation (task 039)** — a background-spawned agent's `tool_result` is an instant ack, not the finished report, and `is_error` cannot distinguish the two; an ack-vs-finished detector is buildable but DEFERRED to task 042. This still applies to CCF's remaining read-only research/review spawns. Full measurements live in `.claude/plan/PLAN.md` (and move to `ARCHIVE.md` when that iteration retires) plus project memory `[[background-agent-result-is-instant-ack]]` — deliberately NOT restated here, because a per-session rule file must carry RULES, not measurement transcripts.

## Shared libs (notable)
- **`lib/archive.mjs`:** the plan-retirement decisions, shared by the DETECTOR (`updatespec-nudge` clause D) and the MUTATOR (`scripts/archive-plan.mjs`) so the two can never disagree about "fully closed". Every function is pure over lines except `findRetirableIterationsIn`, a defensive path-taking reader (missing/unreadable file → `[]`). **Grouping is POSITIONAL — an iteration spans from one `## Origin` heading to the next — never by name.** That is not a style choice: in this repo's own ARCHIVE.md the Origin heading and its Task-backlog heading carry different names (`## Origin — bestpractice-audit → advisor+goal docs → …` vs `## Task backlog — bestpractice-audit + advisor/goal + SubagentStop-gate`) and one backlog heading is the bare `## Task backlog (in execution order)` with no name at all, so name matching would orphan or mis-assign sections and cut the wrong lines. Two guards worth keeping: `isRetirable` requires `rows.length > 0` (because `[].every(...)` is vacuously TRUE, so a brand-new iteration whose backlog table isn't written yet would otherwise read as "fully closed" and be archived on the spot), and both scans skip fenced code blocks so a doc example showing `## Origin …` is not read as a real iteration. `isClosedStatus`/`isRealTaskRow`/`collectTaskRows` are exported from `plan.mjs` for it rather than copied.
- **`lib/io.test.mjs`:** the FIRST test file to exercise `io.mjs` — before it existed, no test file touched `io.mjs` at all, so every one of its exported functions (`readStdinJson`, `emitContext`, `emitSystemMessage`, `blockStop`, `emitStopAdvisory`, `blockUserPrompt`) shipped with zero direct coverage. Because every one of those functions calls `process.exit` itself, they cannot be unit-tested in-process (a `process.exit` call would kill the test runner) — `io.test.mjs` instead spawns `node` as a real CHILD PROCESS per case and asserts the child's actual stdout/exit code. This is the reason the `hooks/lib` suite runs noticeably slower than it would in-process: that cost is the INHERENT price of testing through real process boundaries, not a regression to "optimize away" by dropping process-level spawning. Two of `io.mjs`'s original functions, `blockSubagentStop` and `denyTool`, were removed this iteration once their one caller each (`implementer-verify-gate.mjs`, `plan-review-gate.mjs`) was retired — their tests went with them, not left behind as dead assertions. Retiring `context-guard.mjs` likewise removed its three cases and the mutation-kill test, whose only job was proving two callers shared `buildDualChannelPayload`.
- **Bug this test file caught for real:** the invariant stated everywhere in this file and in `testing.md` — "a hook must never crash on malformed input" — was actually VIOLATED before `io.test.mjs` existed. `readStdinJson()` parsed the literal stdin text `"null"` successfully (it IS valid JSON) but then returned the parsed `null` as-is; a caller hook doing `input.prompt` on that `null` throws a `TypeError`, crashing the hook with exit code 1. No prior test file caught this because none of the pre-existing test files touched `io.mjs`. Fixed in `readStdinJson` by rejecting any parsed value that isn't a plain object (`null`, arrays, numbers, bare strings all now fall back to `{}`) — see the comment in `io.mjs` above.

## Hook-writing conventions
- Each hook starts with `#!/usr/bin/env node` + a comment describing the event, mechanism, role.
- Defensive: wrap every `readdirSync`/`statSync`/`readFileSync` in try/catch, on error → skip the entry (the freshness heuristic is only for nudging, must not break the session).
- Limit recursion depth when walking the tree (e.g. `newestMtime(dir, depth)`); always skip `node_modules` and `.git`.
- Hooks run synchronously and block Claude — keep them fast; `hooks.json` sets a `timeout` (seconds) per hook.
- When adding a new hook: add an entry to `hooks.json` + a comment, reuse `io.mjs`, add the file to `tsconfig.json`'s `include` if it doesn't match the glob.
- **Do NOT declare `"hooks": "./hooks/hooks.json"` in `plugin.json`.** Current Claude Code (v2.1.x) auto-loads `hooks/hooks.json` from the standard location; the `manifest.hooks` field is only for *additional* hook files at a non-standard path (e.g. `./config/hooks.json`). Pointing it back at the standard `hooks/hooks.json` loads the file twice → fatal `Duplicate hooks file detected` and the plugin fails to load. Verify with `claude plugin validate plugins/ccf`. (History: a much older Claude Code did NOT auto-discover and required the field — that behavior was reversed; do not re-add it.)

## Template-shipped hooks (`templates/root/.claude/hooks/*` — a DIFFERENT artifact)
A hook TEMPLATE (e.g. `test-gate.mjs.tmpl`, the opt-in Stop test-gate) is instantiated by `/ccf:init` INTO a target project — it is NOT a CCF-repo hook and obeys different rules:
- **It MAY `exit 2` to BLOCK** (the repo's own Stop hook is deliberately advisory; a target-project opt-in gate is allowed to block — that is its mandate). State this in the file so it isn't "fixed" to advisory.
- **Self-contained**: a target project must not import from the CCF plugin, so COPY the `io.mjs`/`verify-trace.mjs` pattern inline. The ONLY shared piece is a real `.mjs` lib (no `.tmpl`) under `templates/**/lib/` holding the pure decision — so its branchy logic is `node --test`-covered (run `node --test "plugins/ccf/templates/*/.claude/hooks/lib/*.test.mjs"`; the dotted `.claude` MUST be spelled out — a `**` glob skips hidden dirs → 0 tests). Add that lib path to `tsconfig.json` `include`.
- **Hook command uses `$CLAUDE_PROJECT_DIR`** (project root), NOT `${CLAUDE_PLUGIN_ROOT}` (plugin-scoped) — they are different scopes. Presence of the entry in the project's `hooks.json` IS the on/off toggle (no separate settings.json flag).
- **`/ccf:init` must instantiate ALL three** (`test-gate.mjs.tmpl`→`test-gate.mjs`, `hooks.json.tmpl`→`hooks.json`, and the lib **verbatim**), STRIPPING `.tmpl`. Omitting the lib → the hook crashes on a missing import; not stripping `.tmpl` → the loader never finds `hooks.json`.
- **Transcript-scan correctness (two bugs already fixed — do not regress):** (1) **role-gate the scan** — read `tool_use` only from `assistant` lines and `tool_result` only from `user` lines (harness-generated tool output), NEVER scan a user's typed prose, else a chat message containing "FAILED" flips the gate. (2) **a test-FAILED regex must NOT match a passing summary** — "5 passed, **0 failed**" is success; require a failure COUNT `[1-9]\d*` (never `\d+`, which matches the literal 0) and drop the bare word `FAIL`/`FAILED`. Keep this regex in the tested lib (`isFailureText`), not inlined.
