# Hooks (`plugins/ccf/hooks/*.mjs`)

## Absolute invariants
- **No-build, no-dependency, Windows-clean.** Hooks are `.mjs` ESM run directly with `node` (Node ≥ 18). Do NOT add an npm dependency, do NOT add a transpile/bundle step. All I/O via `node:fs`, `node:path`, `node:child_process` built-ins.
- Type-check with `tsc` using `checkJs` + JSDoc (see `tsconfig.json`). Do NOT switch to `.ts`.
- Paths in `hooks.json` use `node "${CLAUDE_PLUGIN_ROOT}/hooks/<file>.mjs"` — this variable ONLY expands in a hook command.

## I/O contract (packaged in `hooks/lib/io.mjs` — reuse it, don't rewrite)
- **Read stdin**: `readStdinJson()` — always returns `{}` on empty/TTY/parse error so the hook NEVER crashes.
- **Inject context (non-blocking)**: `emitContext(eventName, text)` — prints `{ hookSpecificOutput: { hookEventName, additionalContext } }` then `exit 0`. ONLY for events whose schema accepts `additionalContext`: SessionStart, UserPromptSubmit, PostToolUse, **SubagentStart** (the latter adds the string to the spawned subagent's context before its first prompt; cannot block the spawn) and, per the Claude Code 2.1.163 changelog, **Stop and SubagentStop as well** (NOT YET OBSERVED live on this project's harness — see project memory `subagentstop-shape-unconfirmed`). **NOT PreToolUse** — CCF uses only its `permissionDecision`/`permissionDecisionReason` (grounded, PreToolUse ALSO accepts `updatedInput`/`additionalContext`, but CCF does not use them — so don't read this as "deny-only").
- **Warn on a prompt (non-blocking, combined channel)**: `emitPromptWarning(context, message)` — prints the COMBINED `{ hookSpecificOutput: { hookEventName: "UserPromptSubmit", additionalContext }, systemMessage }` payload then `exit 0`. Used by `context-guard.mjs`'s WARN mode so the same advice reaches BOTH the model (`additionalContext`) and the user (`systemMessage`) in one emit; UserPromptSubmit only. Builds on the module-private `buildDualChannelPayload(eventName, context, message)`, shared with `emitStopAdvisory` below (same shape, different event name).
- **Advise at Stop (non-blocking, single-channel — the shipped default)**: `emitSystemMessage(text)` — prints `{ systemMessage }` then `exit 0`. The non-blocking channel for a `Stop` hook (omitting `decision` lets the stop proceed; a `decision: "block"` would force Claude to keep working). This stays the DEFAULT path for `updatespec-nudge.mjs` — see `emitStopAdvisory` below for the opt-in dual-channel sibling.
- **Block at Stop (the "ralph loop")**: `blockStop(reason, systemMessage)` — prints `{ decision: "block", reason, systemMessage }` then `exit 0` (the block is carried by the JSON, NOT an exit code — Stop is the inverse of UserPromptSubmit where exit 2 blocks). `decision:"block"` forces Claude to keep working and feeds `reason` back as the next instruction; the optional `systemMessage` shows the user why. Used by the opt-in `auto-verify.mjs` to drive the verify chain. The opposite of `emitSystemMessage` (advisory).
- **Block at SubagentStop (child-scoped — a DIFFERENT event from Stop)**: `blockSubagentStop(reason)` — prints `{ decision: "block", reason }` then `exit 0`. `decision:"block"` here keeps the SUBAGENT running (scope is child-only; it does NOT affect the main loop) and feeds `reason` back as the subagent's next instruction. Used by the opt-in `implementer-verify-gate.mjs`. Deliberately does NOT reuse `blockStop`: at authoring time (task 034) a SubagentStop payload has no documented `systemMessage` field, so this helper emits only `decision`/`reason` — a narrower shape by design, not an oversight. Per the 2.1.163 changelog, SubagentStop's schema ALSO accepts `additionalContext` in general (see `emitContext` above), but on a BLOCKED SubagentStop specifically, that turn's `additionalContext` is DISCARDED — only the subagent's own final reply reaches the parent session — so `blockSubagentStop` deliberately stays narrow rather than carry a field that would not reach anywhere. NOT YET OBSERVED live on this project's harness.
- **Block a prompt**: `blockUserPrompt(reason)` — writes `reason` to stderr then `exit 2`. UserPromptSubmit only.
- **Deny a tool (PreToolUse)**: `denyTool(reason)` — prints `{ hookSpecificOutput: { hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason } }` then `exit 0`. PreToolUse blocks via this JSON, NOT exit 2; to ALLOW, simply `exit 0` with no output.
- **Advise at Stop, dual-channel (non-blocking, OPT-IN)**: `emitStopAdvisory(context, message)` — prints the SAME combined shape as `emitPromptWarning` but for the `Stop` event name (`{ hookSpecificOutput: { hookEventName: "Stop", additionalContext }, systemMessage }`), via the shared `buildDualChannelPayload`. Per the 2.1.163 changelog, Stop's schema now accepts `additionalContext` — NOT YET OBSERVED live on this project's harness. `updatespec-nudge.mjs` picks the channel with an opt-in `--dual-channel-stop` argv flag: ABSENT (the shipped `hooks.json` state) → `emitSystemMessage` (single-channel, the INVARIANT default that must not change); PRESENT → `emitStopAdvisory`. Same caution level as the `034a` observation gate — stay single-channel until a real post-reload payload confirms the dual shape actually reaches the model.

## Exit code semantics (per Claude Code docs)
- `exit 0` — no decision, the flow continues normally (even after emitting additionalContext).
- `exit 2` — **BLOCK**; stderr is sent back as feedback. This is the only blocking mechanism CCF uses.
- `exit 1` — non-blocking error, does NOT block. CCF avoids it (it adds noise without blocking).

## Events CCF currently uses (`hooks.json`)
- `PreToolUse` (matcher `ExitPlanMode`) → `plan-review-gate.mjs`: enforces that a `/ccf:plan` session reviews its plan before presenting it. Reads `transcript_path` (.jsonl) **best-effort** via `lib/review-trace.mjs` (`hasCcfPlanCommand`/`hasSpecCheckerSpawn`, pure + unit-tested). If it IS a `/ccf:plan` session (a user line matches `/\/ccf:plan\b/` — ONLY the namespaced form; bare `/plan` is Claude Code's own BUILT-IN plan command, not CCF's, and must NOT match) AND no spec-checker spawn is found yet → `denyTool(...)`. **The review detector keys on `subagent_type` (contains `ccf-spec-checker`), accepting a spawn tool named EITHER `Task` OR `Agent` (case-insensitive, `SPAWN_TOOL_NAMES` set).** The spawn-tool name is HARNESS-DEPENDENT — documented as `Task` but surfaced as `Agent` in some runtimes; keying the gate on the name alone DEADLOCKED `Agent`-only harnesses (it never saw the review → blocked `ExitPlanMode` forever). `subagent_type` is the stable gate; the name check only confirms it's a spawn block, so a non-review session still has no match → still allowed (no false positive). Any read/parse failure, or a non-CCF session → `exit 0` (ALLOW): the undocumented transcript shape means we NEVER block wrongly, so this is strong enforcement, not 100% hard — `plan.md` step 6 is the prompt backup. **`hasSpecCheckerSpawn` (renamed this iteration from its previous, more optimistic name):** the old name overclaimed — it only proves the review was CALLED (a spawn `tool_use` appears in the transcript), not that it FINISHED, because since Claude Code 2.1.198 a spawned agent runs in the BACKGROUND by default. The gate's actual behavior is unchanged by the rename (it was always "spawn seen ≥1 time", never a completion check) — the rename only makes the function's true contract honest. The review the gate waits for now also returns a **premortem lens** (`ccf-spec-checker` projects prospective failures anchored to `PLAN.md` "Closed" + project memory); the gate MECHANISM is unchanged — it still keys on `ccf-spec-checker` and is satisfied by the FIRST such spawn it finds (a loop-until-clean plan may produce several; the gate requires ≥1, it does not count them).
- `UserPromptSubmit` → `plan-mode-guard.mjs`: only intervenes on prompts matching `/(^|\s)\/ccf:plan(\s|$)/` — the namespaced form only; bare `/plan` is Claude Code's own built-in plan command and must NOT trigger this guard. Blocks if `permission_mode !== "plan"`. Every other prompt `exit 0` immediately.
- `SessionStart` (matcher `startup|clear|compact`) → `session-start.mjs`: injects the context-first reminder; if CCF-managed, adds a freshness signal + re-loads the active task (in-progress OR in-review, via `findActiveTask`) after `compact`/`clear`.
  - **Freshness signal** (`lib/freshness.mjs`, shared with `updatespec-nudge.mjs`): the PRIMARY signal is git **committer time** (`git log -1 --format=%ct -- <pathspec>` via `spawnSync`, `shell:false` + `encoding:"utf8"`) of the last commit touching code vs spec — NOT mtime, because ordinary git ops (`checkout`/`pull`/`clone`/even a `commit` that touches a code file last) rewrite mtime to "now" regardless of content, which caused a false "spec older than code" nudge. The pure `decideFreshness` only nudges when BOTH git times resolve and `codeGit > specGit`; a `null` git time on either side (not a git repo, git missing, or a path with no commits) **falls back to the depth-limited mtime walk** (`newestMtime`), so freshly-`/ccf:init`-ed non-git projects still work. Best-effort, advisory only, never throws (`gitCommitTime` returns `null` on any error/empty stdout). Decision logic is pure + unit-tested (`lib/freshness.test.mjs`).
- `Stop` → `updatespec-nudge.mjs`: PURELY ADVISORY, never blocks. Surfaces nudges via `emitSystemMessage` (`{ systemMessage }`), NOT `additionalContext` (which `Stop` does not support). Must check `input.stop_hook_active` to avoid loops. Composes **four INDEPENDENT clauses** into the single non-blocking Stop channel (none gates another; all off → emit nothing): **(A) verify-work** — if this SESSION edited a code file but ran no test command (SESSION evidence read best-effort from `transcript_path` via `lib/verify-trace.mjs`: pure `needsVerifyNudge` + the defensive `readTranscriptSignals`/`editedAnyCodeFile`/`isTestCommand` helpers, all unit-tested, never throw), nudge to run the tests/type-check before stopping; **(B) updatespec** — if `specsOlderThanCode` (spec-vs-code staleness across git history, `lib/freshness.mjs`), nudge `/ccf:check` then `/ccf:updatespec`; **(C) plan-status-sync** — if this SESSION ran `git commit` (`lib/git-trace.mjs` `committedThisSession`, the SAME role-gated assistant-`tool_use` shell scan as verify-trace, matching `/\bgit\s+commit\b/`) AND `lib/plan.mjs` `findNonDoneTasks` finds PLAN.md rows still OPEN (todo/in-progress/in-review/blocked/anything else — `done` and a deliberately-abandoned status like `dropped`/`cancelled`/`won't-fix` both count as CLOSED, per `CLOSED_STATUS_RE`), nudge to mark each `done` only after its `/ccf:check` + `/code-review`, or fix its status; **(D) archive-plan** — if `lib/archive.mjs#findRetirableIterationsIn` finds an iteration in PLAN.md whose EVERY task row is closed, nudge to retire it by running `scripts/archive-plan.mjs` (the command string carries an ABSOLUTE path resolved from `import.meta.url`, not from `cwd`, because the plugin runs from its installed cache copy — a cwd-relative path would not exist there). Clause D DETECTS only: the retirement rewrites PLAN.md + ARCHIVE.md and moves task files, so the mutation is deliberately left to the human-run script, the same detection-vs-action split as context-guard's task-040 wording rule. `findNonDoneTasks`/`findActiveTask` resolve the STATUS column **dynamically** from each table's header row (shared `collectTaskRows`), not by assuming it is always the last cell — a real-world PLAN.md that puts another column (e.g. `Predecessor`) after `Status` would otherwise misread that column's value as the status, making every row look "not done" (a real dogfood finding, fixed). `collectTaskRows` ALSO strips markdown emphasis from the status cell (`stripEmphasis`: outer runs of `*`, `_`, backtick, whitespace) before anything interprets it — a SECOND real dogfood finding of the same family: this repo's own PLAN.md wrote `| 036 | … | **done** |` to visually stress the status, and because every status predicate here is anchored (`^done$`, `^in-review$`), the decoration made two finished tasks read as OPEN and clause C named them as unfinished. Emphasis is presentation, not data. Deliberately applied to the status cell ONLY: it is the sole field compared against anchored predicates, while id/title are just displayed. **PLAN.md is also trimmed to the CURRENT iteration** (closed iterations move to `.claude/plan/ARCHIVE.md`, which NO hook reads) — so a closed row left behind in PLAN.md is the other way this count goes wrong, and `/ccf:updatespec` owns that retirement step. The verify-work + plan-status-sync signals key on the HARNESS-DEPENDENT shell-tool name (`bash`/`shell`/`powershell`/`pwsh`) — the `SHELL_TOOL_NAMES` set is COPIED into `git-trace.mjs` (it is module-private in `verify-trace.mjs`, not imported cross-file) — and the harness-dependent edit-tool shape, kept broad so a Windows/PowerShell session or a `MultiEdit` is not a missed signal; both transcript scans are ROLE-GATED to `assistant` lines so user prose ("i will git commit") never false-positives. Despite the filename, the hook is the general CCF Stop nudge, not only the updatespec one. This hook is PURELY ADVISORY — the blocking Stop behavior lives in the separate opt-in `auto-verify.mjs`. **Channel is opt-in dual (task cc-2.1.220-realign):** the default (shipped `hooks.json`, no flag) path calls `io.mjs#emitSystemMessage` — user-facing only, this single-channel behavior is an INVARIANT that must not silently change. Adding `--dual-channel-stop` to its `hooks.json` command switches every clause to `io.mjs#emitStopAdvisory` instead — the SAME advisories, but also relayed to the model via `additionalContext` (per the 2.1.163 changelog's Stop support, NOT YET OBSERVED live on this harness) so the model can restate them `RELAY_IN_USER_LANGUAGE`. The flag is NOT present in the shipped `hooks.json` — default OFF, same caution as the `034a` observation gate.
- `Stop` → `auto-verify.mjs` (a SECOND object in the `Stop` array, alongside `updatespec-nudge.mjs`): OPT-IN and the ONLY CCF Stop hook that can BLOCK. Uses the grounded "ralph loop" (`io.mjs#blockStop` → `{ decision:"block", reason, systemMessage }`) to drive the main loop through the verify chain when there is work to verify. **Opt-in by arg**: it fires only when its `hooks.json` command carries `--auto-verify` (no arg → `exit 0` silently, default OFF — the same toggle pattern as context-guard's `--hard-block`; the hooks.json entry IS the toggle). The drive decision is the pure `lib/verify-chain.mjs#shouldDriveVerify({ enabled, stopHookActive, hasInReviewTask, editedCodeThisSession, checkAlreadyRan })` = `enabled && !stopHookActive && hasInReviewTask && editedCodeThisSession && !checkAlreadyRan`. The five signals REUSE the existing tested helpers (no re-implementation): `enabled` ← `--auto-verify` in argv; `stopHookActive` ← `input.stop_hook_active` (the within-drive loop guard); `hasInReviewTask` ← `lib/plan.mjs#findActiveTask` ≠ null (the trigger — an in-progress/in-review task); `editedCodeThisSession` ← `lib/verify-trace.mjs#readTranscriptSignals().editedCode` (anti-plan-only guard); `checkAlreadyRan` ← `lib/review-trace.mjs#hasSpecCheckerSpawn(parseJsonl(...))` (the cross-Stop guard). When true → `blockStop(buildVerifyReason({ disciplineOn: readDisciplineOn(rulesDir) }), <short systemMessage>)`. `buildVerifyReason` is the ORDERED conditional chain: `/ccf:check` → `/code-review` → (run the project's test command to confirm the contract-level matrix tests pass — ONLY if `readDisciplineOn` finds the "Test design discipline" block + `Matrix required: yes` in `testing.md`; the matrix itself is written by `ccf-implementer` during implement, not a separate command) → `/ccf:updatespec` ONLY when both check + review come back clean (no `FAIL:` finding, the review-marker vocabulary defined in `.claude/rules/prompt-standard.md`); any `FAIL:` → STOP + tell the user, do NOT mark done; if `/code-review` can't self-invoke → run the rest + ask the user. `shouldDriveVerify`/`readDisciplineOn`/`buildVerifyReason` are pure + unit-tested (`lib/verify-chain.test.mjs`); the hook is I/O only. **Loop-guard tradeoff (accepted, and NOT harmless — say so plainly):** `stopHookActive` guards re-entry within ONE drive, and `checkAlreadyRan` is the cross-Stop guard, but `checkAlreadyRan` is now explicitly known to prove only a SPAWN, not a FINISHED review (see `hasSpecCheckerSpawn`'s rename above) — a `ccf-spec-checker` that was spawned but has NOT yet returned (background-by-default since 2.1.198) still reads as `checkAlreadyRan = true`, which SUPPRESSES the entire mandatory verify chain for the rest of this Stop, not just the one already-spawned step. This is accepted because the hook defaults OFF and the advisory `updatespec-nudge.mjs` layer still nudges independently — but it is a real false-negative, not a cosmetic one; do not describe it as harmless. Best-effort: ANY error → `exit 0` (never break a session). Prompt backup: the verify chain is also the documented CCF workflow.
  - **The `Stop` array now holds TWO hooks**: `updatespec-nudge` (default ADVISORY single-channel — `emitSystemMessage`; opt-in dual-channel — `emitStopAdvisory`, only when `--dual-channel-stop` is set — never blocks either way) and `auto-verify` (OPT-IN BLOCKING — `blockStop`, only when `--auto-verify` is set). Mirrors the SubagentStart two-hook arrangement.
- `UserPromptSubmit` → `context-guard.mjs` (a SECOND object in the existing `UserPromptSubmit` array, alongside `plan-mode-guard.mjs`): warns/blocks on a proactive `/compact` when context enters the degrade zone. Reads `transcript_path` (.jsonl) to compute current context tokens (`message.usage` of the last assistant line: input + cache_creation + cache_read, via `lib/context-usage.mjs` `readContextUsage`); `shouldNudgeCompact` is true when tokens are ≥ ~40% of the model window — capped at an absolute ~300k tokens via `NUDGE_ABS_CAP` (40% of a 1M-native Opus/Sonnet-4.x window = 400k is unreachable before auto-compact, so the cap keeps the nudge useful), i.e. the "dumb zone". Two modes, chosen by `decideGuardAction({ aboveThreshold, hardBlock, isEscape })`:
  - **`modelWindowSize` is a MAINTAINED family list, and that is a standing liability.** `LARGE_WINDOW_FAMILIES` (`opus|sonnet|fable|mythos`) enumerates the 1M families; anything unmatched falls through to 200k. A NEW model family that is not added to that list is therefore treated as a 200k window, which quarters the threshold from 300k to 80k and makes the hook nag from very early in a session — this ALREADY HAPPENED with `claude-fable-5` and was fixed only after a user reported the symptom. The fallback direction is wrong on purpose-of-comment vs behavior: the doc comment says "when in doubt guess the LARGER window", but the actual default is the SMALLER one, so silence is not the failure mode. When a new family ships, add it here. The list also accepts a BARE alias as the whole id (`sonnet`, `opus`, `fable`, `mythos` → 1M; `haiku` → 200k) because a transcript line can carry the alias the user typed instead of a full model id (observed live: `"model":"sonnet"`, `"model":"haiku"`); the bare-alias match is anchored to the WHOLE id so a legacy dated snapshot that merely CONTAINS a family name (`claude-3-7-sonnet-20250219`) is still read as 200k.
  - **WARN (default)** — fires every over-threshold prompt, NON-BLOCKING: `emitPromptWarning(modelContext, userMessage)` surfaces the proactive-`/compact` advice through BOTH `systemMessage` (so the USER sees it) and `additionalContext` (so the MODEL is told to relay it) — deterministic, not dependent on the model choosing to repeat it. Hint pre-filled with the hint task (in-progress/in-review, falling back to the next `todo` when none is active, via `lib/plan.mjs#findHintTask` — deliberately NOT `findActiveTask`, so the hint stays task-specific even between finishing one task and starting the next).
  - **Detection/wording split (task 040):** the hook's own DETERMINISTIC job stops at detecting "over threshold" and producing plain FACTS — `lib/context-usage.mjs#normalizeHintTask` returns only `{ id, title } | null`, never a composed sentence. Composing the actual `/compact ...` wording is deliberately left to the MODEL: only it knows what THIS session really changed and what language the user is writing in (the `architecture.md` "Deterministic part vs prompt part" split — detection is certain, but knowing session activity + user language is judgment). So `systemMessage` stays a short, neutral, data-only note, and `additionalContext` carries an INSTRUCTION (via the shared `RELAY_IN_USER_LANGUAGE` clause in `io.mjs`) telling the model to compose the `/compact` command itself, in the user's own language, rather than reusing a canned template. This also sidesteps the language problem for free — a hook cannot know what language the user types in, but a model replying in-language is normal behavior.
  - **HARD-BLOCK (opt-in)** — enabled by adding a `--hard-block` argument to the `context-guard.mjs` command in `hooks.json` (the hooks.json entry IS the toggle, like the template test-gate). Over threshold → `blockUserPrompt(reason)` → `exit 2`, the ONLY deterministic block channel for a UserPromptSubmit (a prompt cannot be merely "suggested" away). **Escape hatch**: an `isEscape` prompt — one whose trimmed text starts with `/compact` (the user is already compacting) OR contains the `ccf:override` token — downgrades block→warn so the user is never trapped.
  - **Compact boundary (just after `/compact`):** `readContextUsage` walks the transcript BACKWARDS and returns null when it hits a `compact_boundary` record BEFORE any assistant line carrying `message.usage` — i.e. right after `/compact`, when no new assistant turn exists yet. Otherwise the hook would read the stale PRE-compact assistant usage (large) and wrongly warn on tokens that no longer exist; returning null keeps the hook silent until the first post-compact assistant turn lands, then it measures the (small, post-compact) context normally. The boundary check runs BEFORE the assistant branch so the two cannot be reordered, and uses a NARROW predicate `isCompactBoundary` (`type:"system"` + `subtype:"compact_boundary"` only — it does NOT read `pre_tokens` nor fall back to `compact_metadata`, so a stray field can never silently suppress the warning; trigger manual|auto are both boundaries).
  - **KISS tradeoff (accepted):** firing on `UserPromptSubmit` (not the old `PostToolUse`) loses MID-TURN detection — a single long turn can cross the threshold without a new prompt — but per-prompt firing is naturally rate-limited (≤ once per user turn), so the old temp-file/`session_id` anti-spam dedup (and its pure decision helper) was REMOVED — no OS-temp state remains. The transcript `.jsonl` shape is **undocumented/internal** → read it **best-effort only**: any error → `readContextUsage` returns null and the hook `exit 0`s silently (never breaks a session). `decideGuardAction`/`shouldNudgeCompact`/`normalizeHintTask`/`isCompactBoundary` are pure + unit-tested (`lib/context-usage.test.mjs`).
- `SubagentStart` (NO matcher — an internal `shouldInject(input.agent_type)` allowlist filters instead) → `agent-rules-inject.mjs`: injects, into every spawned file-WRITING subagent, a directive to read & obey the project coding rules (`.claude/rules/*` + CLAUDE.md) plus the active output style's CODING rules (persona/tone/narration/emoji EXCLUDED), then self-check before finishing. Output styles modify the MAIN loop's system prompt only and are NOT inherited by subagents (grounded `code.claude.com/docs/en/output-styles` + `/en/sub-agents`), so a spawned implementer would otherwise lose both. The allowlist is the `WRITER_AGENTS` set (`{ccf-implementer}`) — read-only research/review agents get a no-op (`exit 0`). The directive reaches the subagent via `emitContext("SubagentStart", …)` (`additionalContext`, "added to the subagent's context before its first prompt"; it cannot block the spawn). All decisions live in the pure `lib/output-style.mjs` (`shouldInject` / `resolveActiveOutputStyle` / `buildInjectDirective`, unit-tested); the hook is I/O only. Best-effort: every fs read is defensive and ANY error → `exit 0` (we MUST never block a spawn). Prompt backup: `ccf-implementer.md`'s body restates the same rules.
- `SubagentStart` (matcher `"Explore"` — the SECOND object in the `SubagentStart` array, alongside `agent-rules-inject`) → `explore-guide-inject.mjs`: injects a short, **language-agnostic, LSP-conditional** exploration directive into the built-in `Explore` subagent so it prefers SEMANTIC navigation (the `LSP` tool — `workspaceSymbol`/`goToDefinition`/`findReferences`/`documentSymbol`, with "no server → just fall back, don't retry") + ripgrep-backed `Grep` + `Glob` over reading whole files. CCF does NOT own the `Explore` agent's prompt (it is a harness artifact), so injecting context at spawn via `additionalContext` is the only deterministic lever (same channel as `agent-rules-inject`). Unlike `agent-rules-inject`, this hook has NO internal `agent_type` filter — the hooks.json `"Explore"` matcher IS the gate; an accidental over-match only adds harmless LSP guidance. Content lives in the pure `lib/explore-guide.mjs` (`buildExploreGuidance`, unit-tested); the hook is I/O only. Best-effort: ANY error → `exit 0` (we MUST never block a spawn).
  - **The `SubagentStart` array now holds TWO hooks**: `agent-rules-inject` (NO matcher → fires for every spawn, narrowed by its internal `WRITER_AGENTS` allowlist) and `explore-guide-inject` (matcher `"Explore"` → the harness pre-filters by agent type, so no internal filter is needed).
- `SubagentStop` (matcher `"ccf-implementer"` — a NEW event array holding exactly ONE hook; do NOT confuse this with the two-hook `SubagentStart` array above) → `implementer-verify-gate.mjs`: OPT-IN (default no-op), blocks a spawned `ccf-implementer` from stopping when its final message carries no `TEST-RESULT:` evidence (the Return-format line pinned in `agents/ccf-implementer.md`). **Opt-in by arg**: fires only when its `hooks.json` command carries `--enforce-tests` (no arg → `exit 0` silently, default OFF — the same toggle pattern as `auto-verify`'s `--auto-verify` / `context-guard`'s `--hard-block`). The drive decision is the pure `lib/implementer-verify.mjs#shouldBlockImplementerStop({ enabled, stopHookActive, agentType, lastMessage })` = `enabled && stopHookActive !== true && isImplementer(agentType) && !implementerReportedTests(lastMessage)` (`stopHookActive` is compared with STRICT `=== true` — a truthy-but-non-boolean value such as the string `"false"`, which a harness could plausibly emit given the field's unconfirmed shape, must NOT be read as the loop guard); `implementerReportedTests` accepts EITHER a real result (`TEST-RESULT: <command> → <pass/fail>`) OR the explicit prose-only declaration (`TEST-RESULT: n/a (no test surface)`), matched only when the `TEST-RESULT:` token starts a line (leading whitespace allowed, `^...m` regex) — a mid-sentence promise like "I will add a TEST-RESULT: line later" is NOT evidence. `agentType` comes from `input.agent_type` (the matcher's own field); `lastMessage` is resolved PRIMARILY from the documented SubagentStop field `input.last_assistant_message` (grounded via code.claude.com/docs/en/hooks + /sub-agents) via `lib/implementer-verify.mjs#resolveLastMessage`, falling back to reading `transcript_path` (NOT a documented field for this event, kept only as a defensive fallback) via `extractLastAssistantText` (reusing the tested `review-trace.mjs#parseJsonl`) ONLY when `last_assistant_message` is absent/empty — an unreadable/missing transcript on that fallback path reads as "no evidence found" (fails safe toward re-asking, never toward silently skipping the check while enabled). When true → `blockSubagentStop(<instruction to add the TEST-RESULT line and finish again>)`. **`stopHookActive` is wired in, but its safety is asymmetric, not a clean "fails safe" — say both directions plainly:** `input.stop_hook_active` is documented per changelog now (NOT YET OBSERVED live on this harness). If the field turns out ABSENT on a real payload, the strict `=== true` check is `false`, so the gate blocks exactly as before — but with no retry counter, that means it can block EVERY SubagentStop for a run that never produces a `TEST-RESULT:` line, i.e. it can loop INDEFINITELY, not just "fail safe once". If the field IS present and the harness sets it `true` already on the very first re-entrant SubagentStop this gate triggers (semantics unconfirmed for a child-scoped event), the gate lets that stop through with zero enforcement even though no evidence was ever reported. Neither direction is a guarantee; do NOT read this gate as airtight in either the "always blocks" or "always retries once" sense until a live payload is observed. **Defensive-by-design (task 034):** SubagentStop's `transcript_path` shape is still UNCONFIRMED by Claude Code docs at authoring time — this hook only trusts `agent_type` + the transcript's last assistant text as a fallback, and `034a` (closed by user acceptance without a live observation) still owes a real captured payload. `shouldBlockImplementerStop`/`isImplementer`/`implementerReportedTests`/`extractLastAssistantText` are pure + unit-tested (`lib/implementer-verify.test.mjs`); the hook is I/O only. Best-effort: ANY error → `exit 0` (we MUST never break a subagent run). Independent of the main-loop `auto-verify.mjs` — this gate is child-scoped and does not drive the main loop's verify chain.
- **Background-spawn observation (task 039)** — a background-spawned agent's `tool_result` is an instant ack, not the finished report, and `is_error` cannot distinguish the two; an ack-vs-finished detector is buildable but DEFERRED to task 042. Full measurements live in `.claude/plan/PLAN.md` (and move to `ARCHIVE.md` when that iteration retires) plus project memory `[[background-agent-result-is-instant-ack]]` — deliberately NOT restated here, because a per-session rule file must carry RULES, not measurement transcripts.

## Shared libs (notable)
- **`lib/archive.mjs`:** the plan-retirement decisions, shared by the DETECTOR (`updatespec-nudge` clause D) and the MUTATOR (`scripts/archive-plan.mjs`) so the two can never disagree about "fully closed". Every function is pure over lines except `findRetirableIterationsIn`, a defensive path-taking reader (missing/unreadable file → `[]`). **Grouping is POSITIONAL — an iteration spans from one `## Origin` heading to the next — never by name.** That is not a style choice: in this repo's own ARCHIVE.md the Origin heading and its Task-backlog heading carry different names (`## Origin — bestpractice-audit → advisor+goal docs → …` vs `## Task backlog — bestpractice-audit + advisor/goal + SubagentStop-gate`) and one backlog heading is the bare `## Task backlog (in execution order)` with no name at all, so name matching would orphan or mis-assign sections and cut the wrong lines. - **`lib/agent-match.mjs` (`matchesAgentName`):** the exact-tail, namespace-tolerant agent-name comparison (`ccf:ccf-implementer` → matches `ccf-implementer`, case-insensitive, EXACT tail after the last `:`, not a loose substring) used by BOTH `output-style.mjs#shouldInject` and `implementer-verify.mjs#isImplementer`. Moved to this neutral file, rather than living inside either hook's own lib, because `implementer-verify.mjs` (SubagentStop domain) previously owned it and `output-style.mjs` (an unrelated SubagentStart domain) had to import FROM it — a dependency direction that reads backwards to anyone who doesn't already know the history.
- **`lib/io.test.mjs`:** the FIRST test file to exercise `io.mjs` — before this iteration, 10 test files existed and none of them touched `io.mjs` at all, so every one of its exported functions (`readStdinJson`, `emitContext`, `emitSystemMessage`, `blockStop`, `blockSubagentStop`, `buildDualChannelPayload`/`emitPromptWarning`/`emitStopAdvisory`, `blockUserPrompt`, `denyTool`) shipped with zero direct coverage. Because every one of those functions calls `process.exit` itself, they cannot be unit-tested in-process (a `process.exit` call would kill the test runner) — `io.test.mjs` instead spawns `node` as a real CHILD PROCESS per case (23 spawns total) and asserts the child's actual stdout/exit code. This is the reason the full `node --test` run grew from ~114ms to ~570ms: that slowdown is the INHERENT price of testing through real process boundaries, not a regression to "optimize away" by deleting the file.
- **Bug this test file caught for real:** the invariant stated everywhere in this file and in `testing.md` — "a hook must never crash on malformed input" — was actually VIOLATED before `io.test.mjs` existed. `readStdinJson()` parsed the literal stdin text `"null"` successfully (it IS valid JSON) but then returned the parsed `null` as-is; a caller hook doing `input.prompt` on that `null` throws a `TypeError`, crashing the hook with exit code 1. No prior test file caught this because none of the 10 pre-existing test files touched `io.mjs`. Fixed in `readStdinJson` by rejecting any parsed value that isn't a plain object (`null`, arrays, numbers, bare strings all now fall back to `{}`) — see the comment in `io.mjs` above.

## Hook-writing conventions
- Each hook starts with `#!/usr/bin/env node` + a comment describing the event, mechanism, role.
- Defensive: wrap every `readdirSync`/`statSync`/`readFileSync` in try/catch, on error → skip the entry (the freshness heuristic is only for nudging, must not break the session).
- Limit recursion depth when walking the tree (e.g. `newestMtime(dir, depth)`); always skip `node_modules` and `.git`.
- Hooks run synchronously and block Claude — keep them fast; `hooks.json` sets a `timeout` (seconds) per hook.
- When adding a new hook: add an entry to `hooks.json` + a comment, reuse `io.mjs`, add the file to `tsconfig.json`'s `include` if it doesn't match the glob.
- **Do NOT declare `"hooks": "./hooks/hooks.json"` in `plugin.json`.** Current Claude Code (v2.1.x) auto-loads `hooks/hooks.json` from the standard location; the `manifest.hooks` field is only for *additional* hook files at a non-standard path (e.g. `./config/hooks.json`). Pointing it back at the standard `hooks/hooks.json` loads the file twice → fatal `Duplicate hooks file detected` and the plugin fails to load. Verify with `claude plugin validate plugins/ccf`. (History: a much older Claude Code did NOT auto-discover and required the field — that behavior was reversed; do not re-add it.)

## Template-shipped hooks (`templates/root/.claude/hooks/*` — a DIFFERENT artifact)
A hook TEMPLATE (e.g. `test-gate.mjs.tmpl`, the opt-in Stop test-gate) is instantiated by `/ccf:init` INTO a target project — it is NOT a CCF-repo hook and obeys different rules:
- **It MAY `exit 2` to BLOCK** (the repo's own Stop hook is deliberately advisory; a target-project opt-in gate is allowed to block — that is its mandate). State this in the file so it isn't "fixed" to advisory.
- **Self-contained**: a target project must not import from the CCF plugin, so COPY the `io.mjs`/`verify-trace.mjs` pattern inline. The ONLY shared piece is a real `.mjs` lib (no `.tmpl`) under `templates/**/lib/` holding the pure decision — so its branchy logic is `node --test`-covered (run `node --test "plugins/ccf/templates/*/.claude/hooks/lib/*.test.mjs"`; the dotted `.claude` MUST be spelled out — a `**` glob skips hidden dirs → 0 tests). Add that lib path to `tsconfig.json` `include`.
- **Hook command uses `$CLAUDE_PROJECT_DIR`** (project root), NOT `${CLAUDE_PLUGIN_ROOT}` (plugin-scoped) — they are different scopes. Presence of the entry in the project's `hooks.json` IS the on/off toggle (no separate settings.json flag).
- **`/ccf:init` must instantiate ALL three** (`test-gate.mjs.tmpl`→`test-gate.mjs`, `hooks.json.tmpl`→`hooks.json`, and the lib **verbatim**), STRIPPING `.tmpl`. Omitting the lib → the hook crashes on a missing import; not stripping `.tmpl` → the loader never finds `hooks.json`.
- **Transcript-scan correctness (two bugs already fixed — do not regress):** (1) **role-gate the scan** — read `tool_use` only from `assistant` lines and `tool_result` only from `user` lines (harness-generated tool output), NEVER scan a user's typed prose, else a chat message containing "FAILED" flips the gate. (2) **a test-FAILED regex must NOT match a passing summary** — "5 passed, **0 failed**" is success; require a failure COUNT `[1-9]\d*` (never `\d+`, which matches the literal 0) and drop the bare word `FAIL`/`FAILED`. Keep this regex in the tested lib (`isFailureText`), not inlined.
